# 082 — ifa's own FA narrowing recognizer hardcoded Python's isinstance/__is__/__nis__ wrapper names

**Status: CLOSED** — fixed 2026-08-07.

### Resolution Summary
Found during a broader audit (prompted by issue 081's `bool_is_numeric` fix) for other pyc-specific behavior baked into `ifa/` without going through the `IFACallbacks` extension-point pattern.

`ifa/analysis/fa.cc`'s issue-025 per-branch type-narrowing recognizer (inside `add_pnode_constraints`'s `if cond:` handling) matched a discriminator call's callee-Sym *name* directly against the string literals `"isinstance"`, `"__is__"`, and `"__nis__"` — Python's own wrapper-call names, hardcoded into ifa's core, generic flow-analysis code with no opt-out. This runs unconditionally for every `if` in every ifa-compiled program, for every frontend. A hypothetical non-Python ifa frontend (there's a real one: the V-language exercised by `ifa/AGENTS.md`'s `make test_llvm`) that happened to define an ordinary function literally named `isinstance`, `__is__`, or `__nis__` for an unrelated purpose would have gotten silently, incorrectly narrowed by ifa's own core FA — a genuine correctness risk, not just missed precision. Structurally identical to issue 081's `bool` lattice-membership bake-in.

**Fix:** added three `IFACallbacks` virtuals (`ifa/ifa.h`): `narrowing_isinstance_name()`, `narrowing_is_none_name()`, `narrowing_is_not_none_name()`, each defaulting to `nullptr` ("this frontend has none of these — recognize nothing," preserving ifa's own generic behavior for any frontend that doesn't override them). `fa.cc`'s narrowing code now looks up these names from `if1->callback` instead of using literals, and only matches when the callback supplies a non-null name (so `nullptr` can never accidentally `strcmp`-match). `PycCallbacks` (`python_ifa.h`) supplies pyc's actual wrapper names — confirmed against `python_ifa_build_if1.cc` and `__pyc__/05_builtins.py`, which are exactly `"isinstance"`, `"__is__"`, `"__nis__"`.

**Verified:** rebuilt clean (a stale incremental build initially produced a spurious, unrelated-looking segfault — `PycCompiler::reanalyze` called from a `c_codegen_pre_file` call site — a vtable-layout mismatch between partially-rebuilt object files, not a real regression; a full `make clean` + rebuild resolved it, same as the earlier false alarm during issue 081's own verification). Full `test_pyc.py` on both backends: 255 pass / 11 expected-fail / 0 fail / 4 skip, unchanged baseline (this exercises the existing isinstance/is-None narrowing test fixtures — `isinstance_union.py`, `isinstance_dynamic.py`, `eq_none.py`, `is_identity.py`, `recursive_list_is_none.py`, etc. — all still pass, confirming the refactor is behavior-preserving for pyc). `ifa --test`: 58/58. `ifa`'s own `make test_llvm` (V-language smoke test, using the default, non-overriding `IRCallbacks`): passes — confirms the default (`nullptr`, no narrowing) leaves ifa's generic/non-pyc behavior untouched.

No new pyc-side test added: this is a pure refactor (pyc's own behavior is unchanged, only *where* the names live moved), and the existing narrowing-dependent test fixtures already provide regression coverage for the override path; the default (no-override) path's safety follows directly from the `nullptr`-guarded `strcmp` calls, exercised by the V-language smoke test.
